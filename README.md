# licence-inventory

Сервіс обліку одиниць з обмеженим строком дії: ліцензій, акаунтів, підписок.
Django 5 + DRF. Покриває повний життєвий цикл одиниці: надходження, видача
клієнту, продовження строку, гарантійне вікно з заміною, нагадування.

Написано як демонстрація роботи з Django: не туторіал і не CRUD-скелет, а
кілька конкретних правил предметної області, доведених до тестів.

## Запустити за хвилину

```bash
python -m venv .venv && . .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
python manage.py migrate
python manage.py seed_demo
python manage.py send_renewal_reminders --days 14
pytest
```

`seed_demo` створює двох клієнтів, шість одиниць, три видачі, одну відкриту
рекламацію і одну прострочену одиницю, яку одразу підмітає `sweep_expired`.

За замовчуванням SQLite, щоб проєкт піднімався без зовнішніх залежностей.
Задано `POSTGRES_DB` в оточенні — код без змін іде в Postgres.

## Що всередині

```
inventory/
  states.py      стани одиниці і білий список переходів
  models.py      моделі, обмеження цілісності на рівні БД
  services.py    уся бізнес-логіка, транзакції, журнал подій
  serializers.py вхід і вихід окремо
  views.py       тонкий HTTP-шар
  management/commands/
    send_renewal_reminders.py   ідемпотентна розсилка під cron
    seed_demo.py                демо-дані
tests/           46 тестів
```

Логіка живе в `services.py`, а не у в'юхах. Тому її видно з тестів, з
management-команди і з адмінки однаково, і вона не дублюється.

## Рішення, які тут насправді цікаві

Нижче сім місць, де очевидна реалізація тихо неправильна. Кожне покрите
тестом, назва тесту вказана поруч.

**1. Продовження рахується від `max(зараз, поточний строк)`, а не від «зараз».**
Клієнт продовжує за 10 днів до кінця на рік. Наївне `now + 365` мовчки з'їдає
ці 10 оплачених днів, і про це дізнаєшся зі скарги, а не з логів. Обидві гілки
перевірені: `test_renewal_does_not_eat_paid_days`, `test_renewal_of_expired_counts_from_now`.

**2. Дві активні видачі одної одиниці неможливі на рівні БД.**
Сервіс бере `select_for_update` і перевіряє стан. Але сервіс можна обійти:
скрипт міграції, адмінка, чужий код. Тому на пару (одиниця, активна видача)
стоїть частковий унікальний індекс, і `test_database_blocks_second_active_issue_even_past_the_service`
перевіряє саме індекс, а не логіку над ним.
Межа чесності: на SQLite `select_for_update` не робить нічого, її підтримує
лише Postgres. Тобто в дефолтній конфігурації від гонки рятує саме індекс, і
це свідомо, а не випадково.

**3. Ідемпотентність нагадувань за ключем (одиниця, тип, строк).**
Не «одиниця», інакше клієнт, що продовжив один раз, більше ніколи не отримає
нагадування. Команду можна ставити в cron хоч щогодини, перезапуск після збою
нічого не дублює: `test_reminder_is_sent_once_per_expiry`,
`test_renewal_opens_a_new_reminder_window`.

**4. Порушене бізнес-правило віддає 409, а не 500.**
500 каже клієнтському коду «спробуй ще раз», і він довбає ендпоінт. 409 каже
«стан не той» і в моніторингу видно окремо від справжніх аварій:
`test_double_issue_returns_409_not_500`.

**5. Жодної зміни стану повз журнал.**
`move_state` єдина точка переходу, вона перевіряє білий список і пише подію.
Журнал тільки на дописування, в адмінці заборонені додавання, зміна і
видалення. Коли клієнт питає «чому акаунт відкликаний», відповідь є в системі,
а не в чиїйсь пам'яті.

**6. Гроші цілими центами, час завжди aware.**
`0.1 + 0.2 != 0.3` виїжджає саме на звірці з платіжкою. Наївний datetime дає
мовчазний зсув на годину двічі на рік, рівно на межі гарантійного вікна.

**7. Налаштування теж покриті тестами.**
`DJANGO_ENV=production` без `DJANGO_SECRET_KEY` падає на старті, а не працює тихо
з ключем із публічного репозиторію. На проді `manage.py check --deploy`
чистий: нуль попереджень, а не «шість, ми знаємо». Локально ж ніяких
секретів не треба, інакше обіцянка «запустити за хвилину» була б неправдою.
Перевірити самому можна так (без `DJANGO_ENV=production` жорсткі налаштування вимкнені,
тому локально попередження будуть, і це очікувано):

```bash
DJANGO_ENV=production DJANGO_SECRET_KEY=$(python -c "import secrets;print(secrets.token_urlsafe(50))") \n  python manage.py check --deploy --fail-level WARNING
```

Всі три сценарії в `tests/test_settings.py`. Там же важлива дрібниця:
`check --deploy` віддає нуль навіть із шістьма попередженнями, тому без
`--fail-level WARNING` такий тест був би декорацією.

Окремо про тести: три перевірки строків спочатку порівнювали результат з
`timezone.now()` через `.days`. Вони проходили поодинці і падали приблизно раз
на три повні прогони. Замінено на коридор між двома замірами часу навколо
виклику. Плаваючий тест гірший за відсутній: він вчить ігнорувати червоне.

## API

| Метод | Шлях | Що робить |
|---|---|---|
| GET | `/api/units/?state=available` | інвентар з фільтром за станом |
| POST | `/api/units/` | завести одиницю |
| POST | `/api/units/{ref}/renew/` | продовжити строк |
| GET | `/api/units/expiring/?days=14` | у кого скоро спливає |
| POST | `/api/issues/` | видати одиницю клієнту |
| POST | `/api/issues/{id}/claim/` | відкрити рекламацію |
| POST | `/api/claims/{id}/approve/` | задовольнити, видати заміну |
| POST | `/api/claims/{id}/reject/` | відхилити |
| GET | `/api/events/?unit_ref=UNIT-001` | журнал по одиниці |
| GET | `/healthz/` | пульс |

Приклад:

```bash
curl -X POST localhost:8000/api/issues/ -H "Content-Type: application/json" \
  -d '{"unit_ref": "UNIT-004", "client_id": 1, "price_cents": 35000, "warranty_days": 7}'
```

## Стани одиниці

```
available ──► reserved ──► issued ──► expired ──► issued (після продовження)
    │            │            │           │
    └────────────┴────────────┴───────────┴──► revoked (термінальний)
```

Усе, чого немає в `ALLOWED_TRANSITIONS`, заборонено і падає з
`IllegalTransition`. Правило лежить одним словником, а не розсіяне по if-ах.

## Чого тут свідомо немає

Щоб не вдавати більше, ніж є:

- **Автентифікації і прав.** Ендпоінти відкриті. Для прода треба DRF-права
  і ролі, це окрема робота, а не рядок у налаштуваннях.
- **Реальної відправки листів.** `send_renewal_reminders` пише подію в журнал
  замість виклику пошти або месенджера. Точка підключення одна, у
  `services.send_renewal_reminders`.
- **Обліку залишків і закупівель.** Собівартість зберігається, звітності по
  марже немає.
- **Асинхронної черги.** На цих обсягах cron або systemd-таймер чесніший за
  Celery з брокером.
